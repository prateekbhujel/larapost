Release & maintenance

How LaraPost versions, validates, tags, releases, and backports changes without turning long-lived branches into a second source of truth.

Versioning

LaraPost follows semantic versioning. Release tags are the source of truth for shipped versions, while main is the only standing development branch.

Branch model

  • main is current development and the active 2.x line.
  • Feature, fix, and release-preparation branches are short lived and deleted after merge.
  • Older maintenance branches are created from the relevant release tag only when a real backport is needed.

Before tagging

  1. Run the full CI matrix.
  2. Run Composer validation, security audit, and the package test suite.
  3. Smoke-test installation in a fresh supported Laravel application.
  4. Run php artisan larapost:doctor.
  5. Verify dashboard access remains protected.
  6. If MCP changed, test authenticated read and write tools with an MCP client.
  7. If provider code changed, test against provider development credentials when available.
  8. Update the changelog, README, docs, and upgrade guide when applicable.
composer validate --strict --no-check-lock
composer audit
composer test
php artisan larapost:doctor

Stable release

Tag the exact green main commit and create the GitHub release from that tag.

git checkout main
git pull --ff-only
git tag vX.Y.Z
git push origin vX.Y.Z
v2.0.0: the v2 release used a guarded workflow that created the release only after the final main CI run succeeded.

Packagist verification

Confirm the tag appears on Packagist and that a clean supported Laravel application can resolve and install the tagged package.

Backport policy

A fix is considered for an older major only when it fixes a real bug or security issue, preserves that release line's documented public contract, includes regression coverage where practical, and does not pull new architecture or features backward.

New providers, new MCP functionality, new queue architecture, and new public APIs are not backported.

  1. Fix and test the issue on main when it still applies there.
  2. Create a maintenance branch from the latest affected release tag.
  3. Cherry-pick or reimplement the minimal fix.
  4. Run the older line's supported CI matrix.
  5. Tag the patch release.
  6. Remove the temporary maintenance branch when it no longer has active work.

Post-release checks

  • Verify the GitHub Pages deployment.
  • Verify Packagist metadata and requirements.
  • Install the tagged package in a clean supported Laravel application.
  • Delete merged preparation branches.
