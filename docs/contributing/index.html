Contributing

A focused contribution workflow for LaraPost code, providers, tests, documentation, and MCP changes.

Target branch

New features, provider work, architecture changes, and bug fixes for the current release line target main. Older maintenance branches are created from release tags only when a real backport is needed.

Development setup

git clone https://github.com/<your-username>/larapost.git
cd larapost
git remote add upstream https://github.com/prateekbhujel/larapost.git
composer install
composer test

Pull request expectations

  • Solve one concrete problem per pull request.
  • Add regression coverage for behavior fixes.
  • Keep provider behavior aligned with current provider documentation.
  • Do not weaken OAuth state checks, route authorization, or MCP authentication to make a test pass.
  • Never commit API tokens, access tokens, client secrets, or production account data.
  • Update public docs when behavior, configuration, commands, or supported platforms change.
  • Treat unrelated CI failures separately rather than changing production code to satisfy them.

Provider changes

A provider pull request should state the provider API/version, required scopes or permissions, media limitations, authentication flow, expected error handling, and how the behavior was tested.

MCP changes

MCP tools that mutate data or publish externally must remain clearly side effecting and must never return provider credentials. Read tools should expose only the data an AI client needs.

Local checks

composer validate --strict --no-check-lock
composer test

The repository CI matrix covers PHP 8.3/Laravel 12, PHP 8.4/Laravel 12, PHP 8.4/Laravel 13, and PHP 8.5/Laravel 13, plus Composer's security audit.

Pull request checklist

  • Tests pass locally.
  • New behavior has regression coverage.
  • Public API or configuration impact is documented.
  • Security implications were considered.
  • Provider restrictions are described accurately.
  • A changelog entry exists for notable user-facing changes.
